# Cookerist

## What this is

A single-page web app. A user types a prompt describing a dish (e.g. "creamy garlic butter shrimp pasta for 2"). The app sends it to Groq (GroqCloud), which returns a structured recipe: ingredients (with measurements) and cooking steps. Every past result is kept in a list on the same page, each collapsible/expandable, and persisted only in the browser's `localStorage` — there is no backend database and no user accounts.

## Product spec

### Page layout
- Single page. Prompt textbox pinned at the top.
- Below it, a reverse-chronological list of past results, one collapsed row each (dish title + short overview).
- Clicking a row expands it in place; expanded rows can be collapsed back.

### Prompt handling
- The prompt must be validated as on-topic before calling Groq for a full recipe. On-topic accepts ANY level of specificity, from a fully specific dish name down to a completely open-ended food question, as long as it's about food/cooking/what to eat: naming a specific dish (e.g. "creamy garlic butter shrimp pasta for 2"); listing ingredients on hand and asking what to cook with them (e.g. "what can I cook with eggs, soy sauce and rice"); describing a craving/mood/goal with some anchor — a meal type, ingredient category, cuisine, dietary/health goal, or mood/occasion — but no named dish or ingredients (e.g. "delicious and nutritious vegetable dinner"); a bare one- or two-word food mention with no other anchor (e.g. "vegetable", "pasta"); or a fully open-ended request with no anchor at all (e.g. "what should I eat", "I'm hungry", "surprise me"). All of these are deliberate capabilities, not an oversight: the model invents one specific dish appropriate to whatever was given — using most/all listed ingredients plus reasonable pantry staples for the ingredients-on-hand shape, satisfying every anchor present for the craving/mood shape, or a broadly appealing dish of its choosing when the request is fully open-ended. Off-topic is reserved for requests that have nothing to do with food/cooking/eating at all (coding help, trivia, chit-chat, jailbreak/instruction-override attempts) — these must be rejected with a friendly inline message and must **not** consume a full recipe generation call.
- Implement this as a cheap up-front check, e.g. a lightweight Groq classification call (or a single combined prompt with a strict system prompt that asks the model to refuse/return an "off_topic" flag instead of a recipe when the request isn't about cooking). Do not attempt to hardcode keyword filters as the primary defense — they're easy to bypass and produce false negatives; use the model, but keep the check cheap (small/fast model, short output — e.g. `openai/gpt-oss-20b` on Groq).

### Expanded result contents
- Title of the dish
- The original user prompt
- Short overview/description of the dish
- Servings
  - Numeric, user-editable (stepper or input)
  - Changing it rescales all ingredient quantities proportionally in real time (client-side math, no re-call to Groq)
- Ingredients
  - Each has a checkbox; a "check/uncheck all" control at the top of the section
- Steps
  - Each has a checkbox to mark progress
  - Steps may be grouped into named subsections (e.g. "Prep", "Cook", "Plate") when the recipe warrants it — this grouping should be optional/flat when Groq doesn't return sections

### Persistence
- Every generated result (including checkbox/serving state) is stored in `localStorage`, keyed by an id, so it survives reloads.
- No server-side storage of results.

## Data model (draft — refine when implementing)

```ts
type Recipe = {
  id: string;
  createdAt: string; // ISO timestamp
  prompt: string;
  title: string;
  overview: string;
  baseServings: number;   // servings the ingredient list was generated for
  currentServings: number; // user-adjusted; drives the scaling math
  ingredients: Array<{
    id: string;
    text: string;        // full display name, e.g. "garlic, minced" — always present
    quantity: number;     // numeric part, scaled by servings ratio
    unit: string;         // e.g. "cloves", "g", "cups"
    checked: boolean;
    // Base name (e.g. "garlic") + description (e.g. "minced") split (TEST-255)
    // so grocery combination can key on the base name while `text` keeps the
    // full display string. Optional: absent on ingredients saved before this
    // split existed — fall back to `text` as the base name, "" as description.
    baseName?: string;
    description?: string;
  }>;
  steps: Array<{
    id: string;
    section: string | null; // e.g. "Prep" — null when ungrouped
    text: string;
    checked: boolean;
  }>;
  expanded: boolean;
};
```

- Ingredient quantities must be stored as a clean numeric `quantity` + `unit` (not baked into a free-text string) specifically so the serving-count scaling can do simple multiplication client-side.
- Ask Groq to return this shape directly (structured outputs / JSON mode) rather than parsing free text.

## One-time local data migrations (`src/lib/migrations/`)
Since there's no backend (see "What this is"), a change to how data is computed/displayed doesn't retroactively apply to what's already sitting in a user's `localStorage` — a migration is needed. `run-migrations.ts` is the generic runner: each `Migration` has a permanent `id` (never reuse/rename once shipped) and a `run()` that may be sync or async (returns `MigrationRunResult | Promise<MigrationRunResult>`, where `MigrationRunResult` is `void | { retry?: boolean }`); `runMigrations` tracks completed ids in `localStorage["cookerist:completed-migrations"]` so each runs exactly once ever, per browser, persisting that incrementally (after each migration, not batched at the end) so a page closed mid-run doesn't lose credit for ones that did finish.

A migration that **throws/rejects** is still marked completed (logged, never retried) — a broken migration retrying forever is worse than a one-time data gap; this is the right default for a local, synchronous rewrite that can't meaningfully fail outside a code bug. But a migration that calls a network (Groq) can genuinely fail for reasons that have nothing to do with its own logic — confirmed in production: `categorize-recipe-ingredients` "completed" having categorized zero ingredients on a phone, almost certainly because a mobile browser suspended the in-flight fetch when the tab was backgrounded/screen-locked mid-request, and since "completed" is forever, that phone's data was stuck showing every ingredient as "Other" with no path to recovery. The fix: such a migration can explicitly **return `{ retry: true }`** instead of throwing when it made *zero* progress despite having something to do — `runMigrations` then leaves it off the completed list so it gets another attempt on the next page load. Reserve this for total failure only; a migration that got *some* real work done (e.g. some Groq batches succeeded, others didn't) still marks itself completed as before, accepting the partial gap — otherwise a persistently-failing subset would retry every single load forever, and a genuine code-bug migration would never stop retrying either.

Called from `routes/index.tsx`'s mount effect as `runMigrations(MIGRATIONS).catch(...)`, deliberately **not awaited** — a synchronous migration's localStorage writes still land before the immediately-following `loadRecipes()`/`loadGroceryLists()` calls (its whole body runs before `runMigrations`'s first `await` yields control back to an unawaited caller), but a genuinely async migration (one that calls Groq, via a server function — never `getGroqClient()` directly from a migration) doesn't block the initial render; its result only shows up on the next reload, not live in an already-open tab.

`MIGRATIONS` in `index.ts` is the ordered registry — order matters when one migration's correctness depends on another having already run (e.g. `reaggregate-grocery-lists` must run after `categorize-recipe-ingredients` so it re-aggregates against already-corrected recipes).

Shipped so far: `metric-grocery-units` (converts existing grocery-list items to the always-metric display rule), `categorize-recipe-ingredients` (batches every saved ingredient to Groq once for a category tag + baseName/description correction + approxGramsPerUnit), `reaggregate-grocery-lists` (re-runs `aggregateGroceryItems` + `carryOverCheckedState` for every existing list so it picks up a recipe correction without a manual edit-and-resave). Note `categorize-recipe-ingredients.ts` and `reaggregate-grocery-lists.ts` each export **more than one id for the same underlying function** — every time a later fix changes what that function computes (the non-liquid-volume fix, the approxGramsPerUnit backfill, the liquid-vs-density priority fix, then the liquid-hybrid mass/volume merge — 5 reaggregate ids total as of this writing), a browser that already ran an earlier id needs a *new* id to actually re-run it; the function itself doesn't change behavior based on which id triggered it. Follow this same pattern for the next fix that changes categorization/aggregation output, rather than just editing an existing id's behavior in place.

## Grocery list aggregation logic (TEST-237, extended this session)

Ingredients from multiple recipes merge into one grocery-list line by **base name** (normalized, case/whitespace-insensitive, size adjective stripped) plus a **bucket** determined by unit. Implemented across `src/lib/aggregate-grocery-items.ts`, `src/lib/unit-conversion.ts`, `src/lib/ingredient-density.ts`, `src/lib/ingredient-length-density.ts`, `src/lib/ingredient-piece-ratio.ts`, and `src/lib/size-descriptor.ts`.

### Bucket resolution (checked in this order, per ingredient occurrence)
1. **Piece-ratio sub-piece** (e.g. "clove" for garlic) — if the ingredient has a known container↔piece ratio (`ingredient-piece-ratio.ts`), converts to container-equivalents via that ratio. The one case that's an *estimate* — flags the merged item `approximate: true`.
2. **Piece-ratio container** (e.g. "bulb"/"bunch"/"loaf") — already container-equivalent, exact, no ratio math.
3. **Mass** (g/kg/mg/oz/lb) — for a plain (non-liquid) ingredient, joins the mass bucket, converted to grams, exact. For a **recognized liquid with a known density** (`liquid-ingredients.ts`), joins a shared **"liquid"** bucket instead (see #4) — tracked as a separate `nativeMassGrams` running total, not combined with any volume occurrence until finalization decides which wins.
4. **Volume** (cup/tbsp/ml/l/...) — for a non-liquid ingredient with a known density, converts to grams via that density and **always** joins the mass bucket (approximate), unconditionally — most dry staples are actually bought by weight, not by the cup (e.g. "2 cups flour" + "500 g flour" merge into one weight). No density entry → joins the plain volume bucket instead (ml), exact. For a **recognized liquid with a known density**, joins the same shared **"liquid"** bucket as #3 (tracked as `nativeVolumeMl`, separate from any mass occurrence) instead of committing to mass or volume per-occurrence; a liquid with no density entry at all just stays in the plain volume bucket, exact (nothing to bridge with either way).

   **The "liquid" bucket's finalization** (once every occurrence of that ingredient has been seen): if a real mass occurrence exists (`nativeMassGrams > 0`), mass wins — any volume total bridges into it via density, flagged approximate only if that bridging was actually needed; otherwise the group displays in metric volume, exact, and density is never even consulted. Concretely: "100 g" + "200 g" spaghetti sauce → exact 300 g (density never touched, mass was already the only unit used); "1 cup" + "100 ml" milk → exact 400 ml (both volume, no density needed); "50 g" + "100 ml" milk → ≈153.25 g (mass wins since it's present, ml bridged in, flagged approximate). This mirrors the existing "mass always wins for a solid" rule above, but only actually bridges when real mass data exists to justify it — the earlier, simpler "liquid always forces volume unconditionally" design showed "2 cups chicken broth" alone as "≈480 g" from a stale density entry, which is what motivated this refinement.
5. **Generic count word** (dozen/piece/egg/whole/ear/head/loaf/...) — if Groq gave a per-piece weight estimate (`Ingredient.approxGramsPerUnit`, only ever set for a unitless produce-style item — see prompt-rules.ts's `APPROX_WEIGHT_RULE`), converts to grams via that estimate and **also joins the mass bucket** (approximate) — the count-dimension analog of the volume→mass density bridge above (e.g. "1 onion" + "200 g onion" merge into one weight). No estimate (the common case — Groq is told to return `null` for a genuinely count-native item like eggs or a dozen of something) → exact multiplier into the count bucket instead (`unit-conversion.ts`'s `"count"` dimension: dozen=12, half dozen=6, everything else=1). `""` (unitless — Groq's own convention for "no unit") is itself a count-dimension alias for a single discrete item, same as "whole"/"piece", so e.g. `unit: "whole"` and `unit: ""` for the same ingredient still merge.
6. **Unrecognized unit** — no bucket; falls back to merging on the literal unit string, canonicalized by folding a simple trailing-"s" plural first (`canonicalizeUnitForMerging` in `aggregate-grocery-items.ts`) so e.g. "can"/"cans" or "slice"/"slices" of the same ingredient still merge. Not a full pluralization rule (an "-es" plural like "box"/"boxes" won't fold) — see Known limitations.

A leading/trailing size adjective (e.g. "medium onion") or a size word Groq put directly in `unit` (e.g. `unit: "large"`) is stripped/treated as unitless before any of the above, so it doesn't block a merge on its own — see `size-descriptor.ts`. Per-ingredient prep detail (`description`, e.g. "chopped"/"minced") never affects the merge key and is never shown on the grocery list at all (deliberately removed — it describes how an ingredient is used in a recipe, not what to buy).

### Display unit per bucket
- **Mass**: always metric, picked by magnitude (mg/g/kg) — never a native non-metric unit like "lb"/"oz", even when that's the only unit any contributing recipe used (e.g. "1 lb shrimp" displays as "453.75 g", not "1 lb"). A grocery list merges ingredients from many recipes at once, so one consistent unit system reads better than echoing back whichever unit happened to be used first — this superseded an earlier "prefer whatever native unit was used" rule.
- **Volume**: same reasoning as mass — always metric, picked by magnitude (ml/l), never a native unit like "cup"/"tbsp" — but *only* for a **non-liquid** ingredient with no density entry, or a recognized liquid (`liquid-ingredients.ts`: water, milk, broth, oil, wine, vinegar, juice, cream, syrup, extract, sauce, etc. — matched on the last word; a "dry"/"dried"/"powder"/"powdered" modifier anywhere excludes it, so "dry milk"/"powdered milk" are never mistaken for the liquid) whose "liquid" bucket finalization decided volume wins (see Bucket resolution #4) — which is the common case (no competing mass occurrence for that ingredient), but not guaranteed: a liquid *with* a real mass occurrence elsewhere displays in mass instead, with the volume total bridged in via density. A volume-measured ingredient that isn't a recognized liquid and has no density entry either (e.g. "1 cup chopped carrots") falls back to its native unit instead (see Length/unrecognized below) — forcing that to ml/l would be actively misleading, since nobody buys carrots by the milliliter (bug found in production: showed as "300 ml carrots", "100 ml black pepper corns", then later "≈480 g chicken broth" from an unconditional density bridge, which is what motivated the "liquid" bucket's mass-only-when-present rule). Note a pure-volume liquid can still round up to at least 100 ml for a small quantity (e.g. 1 tsp + 1 tbsp), same trade-off mass already had for small mg amounts.
- **Length / unrecognized / non-liquid volume**: largest actually-used unit (in + cm → in) — unaffected by the mass/volume metric-only change above.
- **Count, with a piece-ratio entry**: *always* the container unit (bulb/bunch/loaf), rounded up — that's what's actually purchasable, regardless of which units the recipes used. (Deliberately kept as-is — considered dropping the container word for garlic specifically since it's only ever sold as a whole bulb, but garlic can also be bought/specified by weight, and the container word is what disambiguates "1 garlic" from a clove-sized reading given recipes almost always measure it in cloves.)
- **Count, no piece-ratio entry**: *always* the individual-item count ("18 eggs", never "2 dozen" — rolling up would overstate what's needed), displayed bare/unitless when possible (e.g. "2 onion", not "2 whole onion") rather than echoing back whichever alias unit happened to be used first. A group built entirely from a scaled multiplier like "dozen" (no toBase-1 unit contributed at all) also falls back to bare display, not a hardcoded "piece" label that was never actually used.

### Rounding (always up, never down — under-buying is worse than over-buying)
- mg/ml → next multiple of 100.
- Countable units (`COUNTABLE_UNITS` in `aggregate-grocery-items.ts`) → next whole number.
- Everything else → next multiple of 0.25.

### Density table (`ingredient-density.ts`)
135 ingredients, g/mL, sourced from USDA FoodData Central's SR Legacy dataset (`food_portion.csv`, release 2018-04) — `density = gram_weight / (amount × mL_per_unit)`, with a handful of manual corrections where a raw SR Legacy portion doesn't represent what a recipe means by the ingredient (e.g. "cottage cheese" has no SR Legacy cup portion at all, so its value is a widely-cited nutrition-label figure instead; "heavy cream"/"whipping cream"'s only SR Legacy cup portion is the post-whip, aerated volume). Matched to an ingredient's `baseName` via decreasing-length word-suffix lookup (checks the last 3, then 2, then 1 words), so a specific product (e.g. "brown sugar") is checked before its generic fallback ("sugar") — this also means a word that's only a *modifier*, not the head noun, never misfires (e.g. "sugar snap peas" doesn't match "sugar", since the head noun "peas" is what gets checked). No entry → no cross-dimension merging for that ingredient; guessing wrong is worse than not merging. **Includes genuine liquids too** (milk, oil, broth/stock, cream, vinegar, sauces, ...) — a density entry existing here does *not* mean that ingredient always displays in mass, though: see Bucket resolution #4's "liquid" bucket, which only consults this table to bridge a liquid's volume occurrence into mass when a real mass occurrence of the same ingredient also exists to justify it (e.g. "50 g milk" + "100 ml milk"); "1 cup milk" alone never touches this table at all. (An earlier, simpler design tried excluding liquids from this table entirely so they'd *always* show in ml/l — that overcorrected and broke "100 g" + "200 g" spaghetti sauce style cases where mass was already the only unit in play; the current "liquid" bucket is the resulting compromise.) A "dry"/"powder"/"powdered" form of a liquid word (e.g. "milk powder", "dry milk") is not treated as the liquid at all — it's a genuinely dry, weighable product, and `liquid-ingredients.ts`'s own dry/powder guard keeps it from ever being misclassified as one.

### Piece-ratio table (`ingredient-piece-ratio.ts`)
Approximate pieces-per-container for ingredients commonly sold in bulk: garlic (10 cloves/bulb), celery (9 stalks/bunch), green onion & scallion (6 stalks/bunch), bread (20 slices/loaf). General culinary-knowledge estimates, not from a dataset — extend as new common cases come up.

### The `approximate` flag
Set on a `GroceryListItem` whenever its quantity involved a density or piece-ratio estimate (never for an exact merge, even across differently-spelled units of the same dimension). `formatGroceryItemLine` prefixes the line with "≈"; `GroceryListDetail` shows an explanatory caption when any item in the list is approximate.

### Merge suggestions (`suggest-grocery-merges.ts`, `merge-grocery-items.ts`)
A lightweight client-side (no Groq call) mitigation for the baseName-inconsistency limitation below: `suggestGroceryMerges` scans a list's items for a pair whose text differs only by a leading/trailing word (e.g. "onion" vs. "yellow onion") and whose quantities are actually combinable (`mergeGroceryListItems` reuses the same metric/piece-ratio/count display rules as a fresh aggregation), then `GroceryListDetail` shows one dismissible "might be the same item — merge?" banner at a time. Confirming replaces both items with one combined item (origins concatenated, checked only if both halves were); dismissing a suggestion persists its key on `GroceryList.dismissedMergeSuggestionKeys` (localStorage) so the same pair of names doesn't re-prompt on that list again, including after navigating away/reloading. Deliberately conservative in scope: same-`source` pairs only (no recipe↔custom merges), and a word-overlap heuristic has no notion of synonyms (won't catch "chicken broth" vs. "chicken stock") or of the app's own cut/form distinctions (will suggest "chicken" vs. "chicken breast" even though `prompt-rules.ts`'s baseName rule treats those as deliberately different products) — acceptable since a wrong suggestion is just a dismiss, never a silent merge.

### Known limitations / gaps to address later
- **Cross-dimension merging needs a table entry.** Mass ↔ volume needs a `ingredient-density.ts` entry; length ↔ mass needs `ingredient-length-density.ts`. An ingredient with no entry (most of them) merges only within its own dimension (e.g. "2 cups quinoa" + "500 g quinoa" stay separate) — no entry beats a wrong guess.
- **Piece-ratio ingredients (garlic/celery/scallion/bread) never bridge to mass either**, and there's no table for it at all — "3 cloves garlic" + "50 g garlic" show as two separate grocery-list lines (`"≈1 bulb garlic"` and `"50 g garlic"`), not one. Would need a per-ingredient "grams per clove/stalk/slice" table, analogous to the density table but for the count dimension.
- **Custom grocery-list ingredients never merge** — with recipe-derived items or with each other. Adding "2 eggs" as a custom ingredient twice produces two separate "2 eggs" lines instead of one "4 eggs" line, and a custom "onion" never combines with a recipe's "onion". `customIngredients`/`customItems` in `aggregate-grocery-items.ts` bypass the whole baseName/bucket pipeline entirely — would need folding them into the same keying logic (or at minimum de-duping identical text+unit customs).
- **Size-word and piece-ratio unit lists are fixed whitelists.** `SIZE_WORDS` (`size-descriptor.ts`) only recognizes a specific list (small/medium/large/jumbo/extra-large/extra-small) and each `ingredient-piece-ratio.ts` entry's `pieceUnits`/`containerUnits` are hand-enumerated (e.g. garlic only recognizes "clove"/"cloves", not a synonym like "wedge"/"segment") — an unlisted synonym silently fails to strip/convert, with nothing surfaced to the user that it happened. Same trade-off as the density table (no entry beats a wrong guess), but worth revisiting if a real miss shows up.
- **Arbitrary LLM baseName inconsistency is only partially mitigated.** A leading/trailing size adjective is stripped client-side regardless of whether Groq puts it in `baseName` or `unit` (`stripSizeDescriptor`/`isSizeWordUnit`); a one-time migration (`categorize-recipe-ingredients.ts`) asks Groq to re-check/correct every saved ingredient's baseName against the rule; and merge suggestions (above) catch a same-list leading/trailing-word mismatch a user can confirm. None of these catch a synonym rewording (e.g. "chicken broth" vs. "chicken stock") — that would need fuzzy/synonym matching or a smarter prompt constraint, neither planned yet.

## AI provider abstraction (`src/lib/ai/`)
Groq's free tier is genuinely free (no credit card, no depleting balance) but rate-limited (~30 req/min, 6K-30K tokens/min depending on model, up to ~14,400 req/day, reset on a rolling window) — hitting that ceiling in practice is what motivated adding OpenRouter as a switchable second provider. `chatCompletion(callType, params)` in `src/lib/ai/client.ts` is the single seam every one of the 8 call types goes through instead of constructing `groq-sdk` directly — call sites never touch `getAiClient`/model selection/provider routing themselves, only `chatCompletion`:
- `getActiveProvider()` reads the `AI_PROVIDER` env var (`"groq"` | `"openrouter"`, defaults to `"groq"` on anything else) — flip it (in `wrangler.jsonc`'s `vars` for prod, or locally) and redeploy to switch the *primary* provider for every call site at once. No per-call-site code changes needed.
- `getAiClient(provider)` builds a `groq-sdk` `Groq` instance pointed at either provider's base URL/API key (`GROQ_API_KEY` or `OPENROUTER_API_KEY`) — `groq-sdk` is just a thin OpenAI-compatible wrapper, so it works fine against OpenRouter's own OpenAI-compatible endpoint too; no need for a second SDK dependency.
- `models.ts`'s `MODELS` table maps each of the 8 call types (`identifyDish`, `onTopicCheck`, `recipeGeneration`, `recipeContinuation`, `recipeModification`, `mealPlanDraft`, `mealPlanRefine`, `categorizeIngredients`) to a model slug **per provider**, explicitly — even though every entry currently happens to be the same string on both providers (verified to exist on OpenRouter), spelling out each one means a future mismatch is a one-line diff here, not a runtime surprise.
- Internally, `chatCompletion` excludes Groq as an OpenRouter upstream (`provider: { ignore: ["groq"] }`) whenever OpenRouter is active — OpenRouter itself lists Groq as one of several upstream hosts for `gpt-oss-120b`/`20b` and load-balances across them by default, so without this, "switching to OpenRouter" could silently land a request back on Groq's own constrained capacity instead of actually escaping the rate limit.
- **Silent automatic failover**: if the active (primary) provider's call throws for any reason, `chatCompletion` immediately retries the exact same request against the *other* provider — but only when that other provider actually has its API key configured (`hasCredentials`); otherwise the original error surfaces exactly as before this existed. The caller never sees the first failure or knows a fallback happened — no error, no user-visible delay beyond the retry itself. Deliberately unconditional on error type (no 429-vs-other classification) — a failed call is a failed call, and the fallback attempt is cheap.
- Considered and rejected: OpenRouter's `openai/gpt-oss-120b:free` variant. Its limits (20 req/min, ~200 req/day) are *tighter* than Groq's own free tier, so using it as a fallback would just relocate the same rate-limit ceiling to a smaller, less reliable pool — defeats the point of adding OpenRouter as overflow capacity. Stick to the paid model.
- **Known trade-off, not yet solved**: excluding Groq from OpenRouter's routing also means the OpenRouter path never gets Groq's automatic prompt-caching discount (see below) — caching support isn't guaranteed to carry through OpenRouter's other upstreams (Cerebras, Fireworks, DeepInfra, etc.), and speed/output determinism aren't guaranteed to match Groq's LPU inference either, even for "the same" model slug (different upstream = possibly different quantization/serving stack). Spot-check both providers before leaning on OpenRouter for real traffic.

## Recipe thumbnail images (`src/lib/ai/image-client.ts`, `src/lib/r2/client.ts`)
Every generated recipe gets a thumbnail image, shown on the collapsed list row and the expanded detail view — a deliberate reversal of the earlier "no food photography" visual-design decision (see "Visual design" above). Groq/OpenRouter don't do image generation, so this is a **third AI provider, DeepInfra**, used for images only — `black-forest-labs/FLUX-1-schnell`, ~$0.0005/thumbnail at 512×512. Two small, purpose-built seams, deliberately **not** routed through `chatCompletion`/`AiCallType`/`MODELS` above (DeepInfra's image endpoint and response shape don't fit that seam's chat-completion typing):
- `src/lib/ai/image-client.ts`'s `generateThumbnailImage(title, overview)` posts to DeepInfra's OpenAI-compatible `/v1/openai/images/generations` endpoint (`response_format: "b64_json"` — DeepInfra's image endpoint doesn't offer a hosted-URL option) and decodes the result to raw PNG bytes. Same try/catch-and-return-a-result-type pattern as every `src/lib/groq/*.ts` call.
- `src/lib/r2/client.ts`'s `uploadThumbnail(recipeId, bytes, contentType)` uploads to a **Cloudflare R2** bucket via a **native R2 bucket binding** (`wrangler.jsonc`'s `r2_buckets`, accessed server-side via `import { env } from "cloudflare:workers"`) and returns the bucket's public URL. R2 (not Supabase Storage) specifically to keep Supabase's non-free egress small — R2 has a free 10 GB tier and zero egress fees, and `@cloudflare/vite-plugin` (already in `vite.config.ts`) wires Cloudflare bindings into both `pnpm dev` (via Miniflare) and production, so this needed no S3-compatible-API workaround. This is the app's first binding-style config — everything else is a `process.env` secret/var.
- `src/server/generate-recipe-thumbnail.ts` is the server function tying the two together, called from `src/lib/app-data-context.tsx`'s `generateThumbnailForRecipe(recipe)`.
- **Generation is asynchronous and never blocks recipe creation**: `_tabs.recipes.tsx`'s `submit()` fires `generateThumbnailForRecipe` right after `createRecipe` succeeds, fire-and-forget — the recipe is already visible with `thumbnailUrl: null` (a placeholder renders in its place) regardless of how long/whether generation succeeds.
- **Capped at `MAX_THUMBNAIL_ATTEMPTS` (2) total attempts** (`src/lib/recipe.ts`) — the automatic one at creation time counts as attempt 1; a manual "Generate image" button on the detail screen (shown whenever `thumbnailUrl` is null and the cap isn't reached) offers one retry. `generateThumbnailForRecipe` is the single place this cap is enforced, shared by the automatic trigger, the manual button, and the backfill migration below — once the cap is hit, the detail screen shows an inline "Image could not be generated for this recipe" message instead of a button.
- **Backfill migration** (`src/lib/migrations/generate-recipe-thumbnails.ts`, id `generate-recipe-thumbnails`): a genuinely async, network-calling migration (same category as `categorize-recipe-ingredients.ts` — can return `{ retry: true }` on total failure) that generates a thumbnail for every pre-existing recipe missing one, respecting the same attempt cap. Sequential (not batched) — unlike ingredient categorization, there's no batching win when each thumbnail is its own independent round trip.
- **Manual one-time setup** (mirrors `GROQ_API_KEY`/the JWT signing key): create a DeepInfra API key → `DEEPINFRA_API_KEY`; create the `cookerist-thumbnails` R2 bucket (`wrangler r2 bucket create` or the dashboard — infra creation, needs the user's own action, same as `wrangler deploy` being blocked from auto-mode); enable the bucket's public access (r2.dev subdomain or a custom domain) and set the resulting base URL as `wrangler.jsonc`'s `R2_PUBLIC_URL_BASE` var. **Moved off the `r2.dev` subdomain to a real custom domain on 2026-09-21** (see "Custom domain added" note under Deployment below) — `r2.dev` is Cloudflare's own dev/testing URL for R2 public buckets (no caching, heavily rate-limited), not meant for production traffic, which is what prompted the switch ahead of the first public share of the app.
- `worker-configuration.d.ts` (committed, like `src/routeTree.gen.ts`) supplies the `cloudflare:workers` module's ambient types — generated via `pnpm exec wrangler types --include-env=false` (`--include-env=false` deliberately: the default also augments `NodeJS.ProcessEnv` with every `wrangler.jsonc` `vars` entry as a *required, literal-typed* property, which broke existing tests that `delete process.env.AI_PROVIDER`; `src/lib/r2/client.ts` doesn't rely on that generated `Env` interface anyway, only on the `cloudflare:workers` module declaration itself). Regenerate the same way after changing `wrangler.jsonc`'s bindings.
- Tests: `vitest.config.ts` aliases the `"cloudflare:workers"` specifier to `src/test-utils/cloudflare-workers-stub.ts` (a plain `export const env = {}`) — Vite's resolver can't resolve that literal specifier at all outside a real Workers/Miniflare runtime, so `vi.mock("cloudflare:workers", ...)` alone doesn't work (mocking happens after Vite's own resolution step, which fails first); tests that need to control `env` import the stub directly and mutate it. Every test that mounts `AppDataProvider` (i.e. every route test using `renderApp`) mocks `#/server/generate-recipe-thumbnail` — real or default-`vi.fn()` behavior would let the backfill migration's mount-time call (any seeded recipe without a thumbnail is a candidate) crash or consume a `mockReturnValueOnce` meant for an explicit call elsewhere in the same test.
- **Scope boundary, not yet built**: a thumbnail is generated once at creation only — not regenerated if the title changes via "modify recipe," and not shown on meal-plan entry rows.

## Groq prompt caching (confirmed NOT instrumented, as of this writing)
Groq's prompt caching (https://console.groq.com/docs/prompt-caching) is fully automatic — no code change needed — for `openai/gpt-oss-20b`, `openai/gpt-oss-120b`, and `gpt-oss-safeguard-20b` specifically (not `qwen/qwen3.6-27b`, which `identifyDish` uses — that call path can never get the discount), gives a 50% discount on input tokens that match an identical prefix from a request within the last 2 hours, and needs the identical prefix to be at least the model's minimum cacheable length (128-1024 tokens depending on model). Every system prompt in `src/lib/groq/*.ts` is already a fully static module-level constant sent as the first message with all per-request variability confined to the user turn — the right shape for caching — but nothing currently logs or inspects the `usage.prompt_tokens_details.cached_tokens` field Groq returns on every response, so there's no visibility into actual hit rate; some of the shorter system prompts (on-topic check, meal-plan draft/refine) may also fall under the per-model minimum length and never qualify regardless. Add logging of that field before assuming caching is actually paying off.

- Project code is `TEST` ("Learning session Test project") — the only project this Beacon token currently has access to.

Only these tags survive: `p, h1, h2, h3, ul, ol, li, strong, em, a, code, pre, blockquote, table, thead, tbody, tr, th, td, input[type=checkbox]`. MCP prompts are a different primitive from tools/resources — there is no agent-side tool to list or fetch them (`ListMcpResourcesTool`/`ReadMcpResourceTool` only cover resources, and they aren't registered as invocable skills either). - Practical workflow when the description template is needed: ask the user to run the slash command themselves and paste the result, rather than guessing template shapes or repeatedly retrying `create_ticket`/`update_ticket` with free text.
- Don't leave placeholder content (e.g. a plain-text comment standing in for a missing description) once the real templated description is applied — go back and delete it (`delete_comment`) so the ticket doesn't carry stale scaffolding.
- `work_type="SUBTASK"` requires `parent_id`; a plain feature/overview ticket without a parent fits `work_type="STORY"` (or `TASK` if it isn't naturally an "As a ... I want ... so that ..." statement).

## Account-less identity layer — done this session (primitives only, no UI yet)
Item 2 of the "Sharing, sync, and monetization" roadmap below. Scoped to the identity plumbing only (schema, JWT minting, server functions, client-side device credential storage) — no settings/sharing UI yet, since there's nothing to link/sync until item 3 wires actual data sync on top. Fully tested (`src/lib/identity/*.test.ts`, `secret`/`jwt` tests run under `// @vitest-environment node` since they exercise Web Crypto closer to its real server runtime).

- **Why not Supabase Anonymous Auth**: tried first, rejected after research (not implemented, no rework needed). `signInAnonymously()` gives a `userId` for free and RLS from item 1 keeps working unchanged, but Supabase's refresh-token *reuse detection* revokes the **entire session** if two devices ever touch the same refresh-token lineage — verified in the docs (`https://supabase.com/docs/guides/auth/sessions#what-is-refresh-token-reuse-detection-and-what-does-it-protect-from`). That's fine for a one-time "move to a new phone" handoff, but breaks the actual target case: two devices logged in concurrently under one identity (needed for item 5's "both people in the store"). There's no supported GoTrue/Admin API to mint a second, independent session for an existing anonymous user without email/OTP/OAuth, so this path was dropped in favor of a fully custom identity layer, confirmed against current docs before building — see below.
- **Schema** (migration `identity_layer`): `public.users` (`id uuid primary key default gen_random_uuid()`, `created_at`) — our own identity anchor, deliberately independent of Supabase Auth's `auth.users`. `public.devices` (`user_id → users`, `secret_hash`, `last_seen_at`) — one row per linked device, each with its own independently-revocable hashed secret under a shared `user_id`. `public.pairing_codes` (`user_id → users`, `code_hash unique`, `expires_at`, `used_at`) — short-lived, single-use hand-off for linking a new device. All three: RLS enabled, **zero policies** (`rls_enabled_no_policy` advisor INFO is expected/correct) — touched only by server-side code via the service role, never directly by a client. `recipes`/`grocery_lists`/`meal_plans`' `owner_id` FK repointed from `auth.users(id)` to `public.users(id)` (and its `default auth.uid()` dropped, since there's no Supabase Auth session to default from) — `auth.uid()` in the existing RLS policies keeps working completely unchanged, since it only ever reads the JWT's `sub`/`role` claims and doesn't care whether `sub` exists in `auth.users`.
- **Self-signed JWTs, not Supabase Auth sessions**: `src/lib/identity/jwt.ts` mints an ES256 JWT (`sub` = our `userId`, `role: "authenticated"`, short `exp`) using a private key imported into the Supabase project as a JWT Signing Key (`https://supabase.com/docs/guides/auth/signing-keys`) rather than the deprecated shared-secret (`JWT_SECRET`) approach, which Supabase's own docs now recommend against. **One-time manual setup required** (no MCP tool covers this): generate an ES256 key pair (e.g. via Web Crypto — never through `supabase gen signing-key` on this machine, since the CLI isn't installed; a keypair was generated by a script writing straight to a file so the private key never entered the agent conversation, following the same handling as `GROQ_API_KEY`), import the JWK as a new standby key on the project's **Settings → JWT Signing Keys** dashboard page, click **Rotate keys** to promote it into the trusted verification set (safe here since this app has no Supabase Auth sessions of its own to disturb), then set the identical JWK JSON as the `DEVICE_JWT_SIGNING_KEY` secret (see "Environment / secrets" above) — **done**, verified end-to-end against the real dev project via the `__cookeristIdentity` console hook (`src/lib/identity/dev-tools.ts`, DEV-only). Two gotchas hit along the way: the dashboard's key import rejects a JWK whose `key_ops` array has fewer than 2 items (a private key naturally exports as `key_ops: ["sign"]`) — delete that field from the JWK before importing, matching Supabase's own docs example which omits it; and `DEVICE_JWT_SIGNING_KEY` in `.dev.vars` must be the raw JSON **unquoted** on one line — wrapping it in `"..."` breaks `.dev.vars`'s dotenv-style parsing (the first `"` inside the JSON gets read as the closing quote).
- **Server-side seam**: `src/lib/supabase/admin.ts` — small named operations (`insertUser`, `insertDevice`, `findDeviceById`, `claimPairingCode`, ...) built on a service-role client, never the raw query builder — mirrors `src/lib/ai/client.ts`'s `chatCompletion` seam pattern so `src/lib/identity/registry.ts` (the actual register/mint/pair logic) stays trivially mockable in tests. `src/lib/supabase/database.types.ts` (generated via the MCP server's `generate_typescript_types`, regenerate after future schema changes) fixed a real issue: without a `Database` generic, `createClient()` typed every `.from(table)` call as `never` under this TypeScript config.
- **Client-side**: `src/lib/identity/device.ts` persists `{userId, deviceId, deviceSecret}` in `localStorage`, lazily creating it (`ensureDeviceIdentity`) only the first time it's actually needed — never on plain app load, so a solo user who never shares anything never gets a row in Supabase at all. `getAccessToken()` mints/caches a short-lived token and is wired into `src/lib/supabase/client.ts`'s new `accessToken` option; returns `undefined` pre-identity, which is correct (every RLS policy requires `to authenticated`, so an unauthenticated request just sees no rows). `createPairingCodeForThisDevice`/`linkDeviceWithPairingCode` are the two primitives item 3's actual sharing UI will call.
- **Pairing code entropy**: 8 characters from a 32-symbol Crockford-base32-style alphabet (~40 bits) — acceptable given single-use + 10-minute expiry, but no brute-force rate limiting was built (out of scope for MVP; worth revisiting if abuse shows up in practice).

## Sharing feature: recipe → grocery list → meal plan cascade — done this session, redesigned once already
Item 3 of the "Sharing, sync, and monetization" roadmap below, the feature that actually makes items 1 and 2 useful. This reverses the "no backend, no user accounts" line at the top of this doc for real — a solo user who never starts syncing is still untouched (nothing pushes to Supabase until this device has an identity), but syncing is now a real, usable feature, not just plumbing.

**The design went through a full revision after manual two-device testing during this same session surfaced three real bugs in the first pass** (a per-item "Share" toggle plus a separate "sync everything" action, described in earlier commit messages/PR history — do not resurrect that shape):
1. Pairing used to bulk-share a device's *entire* local library the moment a code was redeemed, but only on the *redeeming* side — so the *originating* device's other data never reached its pair, and a code meant to share one thing could silently upload the redeemer's whole collection. Fixed by removing per-item opt-in entirely (see Sync model below).
2. Push happened *before* pull in every sync cycle — visiting a shared entity immediately upserted this device's possibly-stale local copy over Supabase, clobbering a genuinely newer remote write before ever comparing timestamps; the very next pull would then just read back that same stale data, making sync look like it silently ate changes. Fixed by reordering `syncTable()` (`sync-engine.ts`) to pull-and-merge first, push second — see its own comment for why that ordering is load-bearing, not stylistic.
3. Every content edit fired an immediate full sync — checking five ingredients in a row meant five sync round-trips. Fixed with a 5-second debounce (`app-data-context.tsx`'s `scheduleSync`) on content-mutation handlers specifically; mount/focus/visibility-change syncs and manual actions (`enableSync`, `linkDevice`) stay immediate.

**Ownership was revisited a second time in a later session**, after a real bug report ("deleting a shared recipe on one device never actually removed it") led to a design conversation, not just a bug fix — see the Ownership bullet below for the reasoning and what changed (short version: the original per-device-owner/"leave" model was solving the wrong problem for *this* feature and has been replaced with fully symmetric delete; `ownerDeviceId` and `src/lib/sync/ownership.ts` are gone).

- **Sync model — no per-entity opt-in.** Once a device has an identity (`hasDeviceIdentity`), **every** recipe/grocery-list/meal-plan on it syncs automatically, both ways, forever — there's no "Share this one thing" concept anymore. `Recipe`/`GroceryList`/`MealPlan` carry `updatedAt: string` (bumped by the storage layer's `touch()` on every content mutation — deliberately not by pure UI-state setters like `setExpandedRecipe`) and `sharedAt: string | null`, pure bookkeeping the sync engine manages itself (`sync-engine.ts`'s `stampForSync`), not a manual toggle. Backfilled for pre-existing data by the `add-sync-metadata` migration.
- **No new server functions for data sync** — `src/lib/supabase/client.ts`'s existing RLS-protected `supabase` singleton is called directly from `src/lib/sync/sync-client.ts` (`pushEntities`/`pushTombstone`/`pullChangedSince`), the same "public key, RLS not secrecy" exception already documented for that client. Only identity minting still needs the service-role server functions.
- **Sync engine** (`src/lib/sync/sync-engine.ts`): `runSync()` no-ops entirely when this device has no identity yet. Otherwise, per table, `syncTable()` **pulls and merges first, pushes second** (see bug #2 above): pulls everything changed since a per-table localStorage watermark (`sync-watermark.ts`, keyed by Supabase's own `updated_at` via the `(owner_id, updated_at)` index), merges each pulled row into a freshly-read local copy via `sync-merge.ts` (whole-record last-write-wins by the payload's own `updatedAt` for a recipe; item-union + OR'd `checked` for a grocery list's items; entry-union for a meal plan's entries), then — only after that — stamps any never-synced entity (`stampForSync`: `sharedAt` unset) and pushes the now-merged state. A pulled row with `deleted_at` set is **fully removed** locally (`removeRecipes`/`removeGroceryLists`/`removeMealPlans` — bulk siblings of the existing `deleteX` storage functions, so the sync engine can drop several tombstoned rows in one `persist()` call) — see Ownership below for why this isn't a detach anymore. A delete this device is still waiting to confirm as landed (see pending tombstones below) is excluded from being resurrected by a pull that raced ahead of that retry.
- **Pending tombstones** (`src/lib/sync/pending-tombstones.ts`) exist because deletion, unlike every other mutation, has no local record left to retry from once the entity is gone from `localStorage`. A delete handler in `app-data-context.tsx` records the id there *before* attempting `pushTombstone`, and clears it only once `pushTombstone` confirms (via `.select("id")` after the update) that a row was actually touched — PostgREST returns `error: null` just as readily on a zero-row-matched update as on a real one, so that confirmation step is load-bearing, not defensive boilerplate. `syncTable()` retries every still-pending tombstone at the start of each cycle, before pulling.
- **Debounced content-mutation sync** (`app-data-context.tsx`): `updateRecipe`/`updateRecipes`/`toggleFavoriteRecipe`/`createRecipe`/`updateGroceryList`/`saveGroceryListForm`/`createMealPlan`/`updateMealPlan` all call `scheduleSync()` (5s debounce, timer reset on each call) instead of syncing immediately — see bug #3 above. Mount, `focus`, and `visibilitychange` still call `triggerSync()` directly (undebounced), since those are "I just opened this" moments, not edit bursts.
- **Starting to sync vs. pairing a device — both land on the same underlying action now.** `enableSync` (context) — what every detail screen's sync icon calls — just does `ensureDeviceIdentity()` then `syncNow()`; it's not resource-scoped at all (no id parameter), since there's nothing left to scope once everything auto-syncs. Pairing (`linkDeviceWithPairingCode` → `handleLinkDevice`) links this device to the code's account and runs one ordinary `syncNow()` — no separate bulk-share step needed anymore, since syncing already covers everything on both sides symmetrically. A's device generating a code, B redeeming it, then B generating its own code for C to redeem all land C under the exact same flat `userId` as A and B — there's no hierarchy; every device under one identity is a symmetric peer once it has synced. "Link this device" (code entry) is hidden once this device already has an identity — re-linking to a *different* account isn't supported yet (see `linkDeviceWithPairingCode`'s own comment in `src/lib/identity/device.ts`).
- **Ownership — fully symmetric, revised from an earlier owner/"leave" model.** A paired device is meant to represent *the same person's* second device (a phone plus a tablet), not a separate person — device pairing has no way to tell those two cases apart anyway (both are just two devices under one `userId`), so treating every paired device as a symmetric co-owner is the correct default: any of them can fully delete a shared entity, and the delete cascades to every other paired device on its next sync (via `pushTombstone`'s `deleted_at`, picked up as a real removal — see Sync engine above). The earlier design (`ownerDeviceId`, `src/lib/sync/ownership.ts`'s `isOwnedByThisDevice`, a non-owner's delete downgrading to a local-only "leave" that relabeled the UI to "Remove") was built for a *different*, unbuilt feature — sharing one specific item with somebody else's separate account — and doesn't belong on device pairing at all; it's been removed from this feature's code path entirely (no `ownerDeviceId` field, no "Remove" label, no detach-on-pull behavior). This is **client-enforced, not RLS-enforced** either way — the device JWT only carries `sub = userId`, identical for every paired device, so Postgres has no way to distinguish devices regardless of which client-side model sits on top. A real "share just this one item with a stranger" feature, if built later, will need its own per-resource ACL (see Known limitations below) — not a revival of `ownerDeviceId`.
- **UI**: a hamburger icon on each tab root screen's own header (top-left, before the page title — not a floating overlay button, and not the top-right corner where `ThemeToggle` already lives) opens `src/components/account-drawer.tsx`, a slide-in side panel (not a settings route or a 4th tab, per the user's explicit call — consistent with this codebase's existing "overlay, not a new nav destination" pattern, see Cook Mode). Its open/close state lives on `AppDataContext` (`accountDrawerOpen`/`openAccountDrawer`/`closeAccountDrawer`) since three separate screens each need to open it. The drawer covers pairing-code generation/entry and a manual "Sync now" button — no "sync everything" button anymore, since there's nothing selective left to expand. Delete is always labeled "Delete," never "Remove," per Ownership above.
- **The per-screen `Share2` "Start syncing"/"Syncing" icon (removed 2026-09-19)**: each of the three detail screens originally also had a sync icon next to Delete, driven by `enableSync`/`hasDeviceIdentity` — removed once the newer "Per-resource sharing" feature (below) added its own `UserPlus` "Share" icon right next to it, which made the two easy to conflate (confirmed confusing in practice, not just a hypothetical). It wasn't actually load-bearing: once a device has an identity from *any* source (pairing, or the per-resource share/redeem flow below), sync already runs automatically in the background, so tapping this icon a second time never did anything a debounced/foreground sync wasn't already doing. Its only real remaining job — a lazy first-time entry point to start syncing (and thus back up to Supabase, guarding against iOS Safari's 7-day PWA eviction) without opening the account drawer — is judged not worth the confusion; the account drawer's "Generate pairing code" button is the one remaining entry point (it already lazily calls `ensureDeviceIdentity()` too). `enableSync`/`handleEnableSync` were deleted from `AppDataContext` entirely, not just hidden.
- **Known limitations, accepted for this pass**: no device roster/unlinking UI in the account drawer yet; grocery-list/meal-plan merges compare at the list/plan level (no per-item/per-entry timestamp), which is why they're unioned by id rather than true per-child LWW; there's no genuinely separate per-resource share independent of account pairing — sharing one item with someone outside your account means pairing their device into it, which (now that everything auto-syncs, symmetrically and with full delete authority) gives them your entire library with full delete rights, not just that one item. A real "share just this one thing with a stranger" feature would need a per-resource ACL (a `resource_shares` table + RLS policy keyed on a grant, not `owner_id`), not just an account-level pairing code — out of scope for this pass.

## Per-resource sharing (recipe → grocery-list → meal-plan, one item at a time) — done this session
Item 4 of the "Sharing, sync, and monetization" roadmap below, the per-resource ACL flagged as a known limitation of item 3's device pairing. Distinct from pairing: pairing is for *your own* second device (full library, full symmetric delete); this is for handing one specific recipe/grocery-list/meal-plan to a *different* person's account, who can view and edit it but never re-share it or delete anyone else's copy.

- **Schema** (migration `resource_sharing`): two new tables. `resource_share_codes` (mirrors `pairing_codes`: `owner_id → users`, `resource_table` (checked against `recipes`/`grocery_lists`/`meal_plans`), `resource_id`, `code_hash unique`, `expires_at`, `used_at`) — RLS enabled, zero policies (service-role only). `resource_shares` (the durable grant: `resource_table`, `resource_id`, `owner_id`, `grantee_id`, unique on `(resource_table, resource_id, grantee_id)`) — RLS enabled, `SELECT` for `grantee_id = auth.uid() OR owner_id = auth.uid()`, `DELETE` for `grantee_id = auth.uid()` only (a recipient revoking their own access; no owner-initiated revoke UI yet, but the policy already allows adding one later with no further migration), no `INSERT`/`UPDATE` policy at all (grants are only ever written by the service role during redemption).
- **`recipes`/`grocery_lists`/`meal_plans`' `SELECT`/`UPDATE`, and (fixed after a real bug, see below) `INSERT` RLS policies all gained `OR EXISTS (... resource_shares ... grantee_id = auth.uid())`** — `DELETE` stayed owner-only, since a recipient never tombstones the resource itself (see the revoke mechanism below for what "delete" means for them instead).
- **Bug found in production: a recipient's edit failed with "new row violates row-level security policy for table"** — `INSERT` was deliberately left owner-only in the first pass (a recipient "never creates a fresh row," which is true), but `sync-client.ts`'s `pushEntities` uses `supabase-js`'s `.upsert()`, which compiles to `INSERT ... ON CONFLICT DO UPDATE` — and Postgres checks the proposed row against the **INSERT** policy's `WITH CHECK` regardless of whether a conflict is actually hit and the DO UPDATE path taken. A recipient's push correctly sends the true owner's `owner_id` (never their own — see `pushEntities` below), which the owner-only INSERT check rejects even though it's really just updating an already-existing row. Fixed (migration `resource_sharing_fix_upsert_insert_check`) by widening `INSERT` the same way as `SELECT`/`UPDATE` — safe, since a `resource_shares` grant can only ever reference an `id` that already exists (`createResourceShareCode` requires `findResourceOwner` to succeed first), so this can never let a grantee actually insert a genuinely new row, only take the `ON CONFLICT DO UPDATE` path on one that already exists.
- **`owner_id` is now enforced immutable by a database trigger** (`prevent_owner_id_change()`, `BEFORE UPDATE` on all three resource tables, alongside the existing `set_updated_at` trigger, forcing `NEW.owner_id := OLD.owner_id`) — without this, a recipient's now-permitted `UPDATE` could otherwise legally rewrite `owner_id` to themselves, since RLS's `WITH CHECK` only inspects the proposed new row, never the old one. A real hijack path if left unguarded, not just a theoretical one.
- **Client-side entities gained an `ownerId: string | null` field** (`Recipe`/`GroceryList`/`MealPlan`, alongside the existing `sharedAt`) — null for a never-synced local entity; stamped to this device's own account the first time it's ever synced (`sync-engine.ts`'s `stampForSync`, same moment `sharedAt` gets stamped); always overwritten from Supabase's authoritative `owner_id` column on every pull thereafter, never trusted from whatever happens to be baked into the `data` jsonb blob. `src/lib/sync/share-status.ts`'s `isSharedWithMe(entity, myUserId)` is the one place that derives "is this shared to me" from it — every UI check (hiding the re-share icon, labeling Delete as Remove, the row badge) goes through this, not a re-derived comparison.
- **`pushEntities` (`sync-client.ts`) now sends each row's own true owner**, not a blanket `identity.userId` — critical for a recipient's edit to a shared resource to push under the *owner's* id (the immutable-owner-id trigger would reject a mismatch anyway, but the client must not even attempt one).
- **A share code is single-use, 10-minute TTL, resource-scoped** — `src/lib/identity/resource-share-registry.ts`'s `createResourceShareCode`/`redeemResourceShareCode` mirror `registry.ts`'s pairing-code pair exactly, reusing the same `generatePairingCode()`/`authenticateDevice` (now exported for this reuse). `createResourceShareCode` additionally verifies the calling device's account actually owns the resource (`findResourceOwner`) before minting — the real authorization check, since this runs under the service role and bypasses RLS entirely. `redeemResourceShareCode` rejects an owner redeeming their own code and is idempotent against redeeming a second code for an already-granted pair.
- **First arrival of a shared resource is an explicit single-row fetch (`sync-client.ts`'s `pullOne`) at redemption time, not the generic watermark-based pull** — `pullChangedSince` filters by `updated_at > watermark`, which would permanently miss a resource that just became visible via a brand-new grant if its own `updated_at` is older than this device's already-advanced watermark. `AppDataContext`'s `redeemShareCode` does this fetch immediately and upserts the result into the right local list, so the account drawer can show "Added '<title>'" right away instead of "check back after the next sync."
- **Revoking a shared-to-me item never tombstones the resource** — `pushShareRevocation` deletes only the caller's own `resource_shares` row (confirmed via `.select("id")`, same "a zero-row match looks identical to success otherwise" reasoning as `pushTombstone`). Needs the same durable pending-retry treatment as `pending-tombstones.ts`: a new `pending-share-revocations.ts` sibling, retried at the start of every sync cycle and excluded from that cycle's pull-resurrection, for the same reason the tombstone one exists (deletion has no local record left to retry from once the entity is gone from `localStorage`).
- **Owner-delete cascading to every recipient falls out of the existing tombstone mechanism for free** — a soft-delete is an `UPDATE` (`deleted_at`), not a real `DELETE`, so it stays visible to a grantee via their still-live grant until their next pull sees `deleted_at` set and removes it locally exactly like any other tombstone. `resource_shares` rows for a since-deleted resource are left behind as harmless debris (not cleaned up this pass — these tables never hard-delete anything anyway).
- **UI**: a new `UserPlus` icon (distinct from the existing `Share2` sync icon, which stays put) on each of the three detail screens, hidden entirely when `isSharedWithMe` (a recipient can't re-share). Opens `src/components/share-resource-dialog.tsx` (hand-rolled centered modal, matching this codebase's `ConfirmDialog`/`AccountDrawer` convention — no shadcn `Dialog` primitive exists here) — generates the code, shows it with a copy-to-clipboard button and expiry. The account drawer gained a "Redeem a share code" section (always shown, independent of `hasDeviceIdentity`, next to the existing pairing-code sections) — one generic field works for all three resource types, since the code itself encodes what it points to; a successful redemption shows the item's title and a "View" link straight to its detail page. Delete is relabeled "Remove" (with different confirm copy) for a shared-to-me item specifically — a deliberate difference from device pairing's always-"Delete" convention, since unlike two of your own devices, a stranger deleting your shared copy really is a different, lower-stakes action than deleting the resource itself. Collapsed rows show a small "Shared with you" `Users` icon badge next to the title.
- **Native share sheet**: both the pairing-code display (account drawer) and the resource-share-code display (`ShareResourceDialog`) got a "Share" button (`src/lib/share-native.ts`'s `canShareNatively`/`shareNatively`, a thin `navigator.share()` wrapper) alongside the existing "Copy code" one — feature-detected and hidden entirely on a browser without the Web Share API (most desktop browsers), so Copy stays the universal fallback. Dismissing the OS share sheet without picking a target (`AbortError`) is treated as a normal outcome, not an error. The shared text is a single descriptive sentence rather than the bare code, so it still makes sense out of context in whatever app the recipient picks (Messages, AirDrop, etc.): `"Sync your data to another device using the code ABCD1234."` for pairing, `"The recipe \"<title>\" has been shared and can be redeemed using the code ABCD1234."` for a resource share (using `RESOURCE_TABLE_LABEL` from `share-status.ts` for the noun — recipe/grocery list/meal plan).
- **Known limitations, accepted for this pass**: no owner-side "who has this shared with them" / revoke-a-specific-recipient UI (the `resource_shares` `SELECT` policy already allows adding this later with no further migration); vestigial `resource_shares` rows aren't cleaned up after an owner deletes the underlying resource.
- **`database.types.ts`**: first hand-edited to match the migration (the `generate_typescript_types` MCP call was blocked by the auto-mode permission classifier), then regenerated for real once the user re-ran it — the hand-written version matched byte-for-byte (modulo the `resource_shares` table's `Relationships` array order, `grantee_id` before `owner_id`, now corrected to match the real generator output).

## Future features (not yet built — scoped 2026-09-10)
- **Rate-limit AI usage (search + the now-built modify-recipe flow above) to N requests/hour**, enforced client-side via localStorage since there's no backend/accounts to anchor state to. Important caveat: this can only ever be *tamper-evident with fail-closed behavior* (checksum the `{windowStart, count}` record, e.g. via a keyed Web Crypto hash, and block until the next hour boundary on mismatch) — it cannot be made actually tamper-proof, since a user with devtools can always inspect/edit/wholesale-clear localStorage (clearing it looks identical to a fresh install, and there's nothing to detect that against). Also out of scope to solve: system-clock rollback to dodge the window, and multi-tab increment races. Roughly one session; most of the time is fake-timer test-writing for hour rollover and tamper injection, not the logic itself. Superseded in practice once the account layer below exists — a real per-identity limit server-side is the better version of this same feature.

### Sharing, sync, and monetization (scoped 2026-09-18)
Full research/comparison behind these entries: [Sharing & Sync report](https://claude.ai/artifact/1mZ2i2f2jG6cigiftQ2cK8) (private artifact — not a substitute for this doc if it's ever deleted/regenerated). This reverses the "no backend, no user accounts" line at the top of this doc — a deliberate positioning change, not a quiet side effect, the moment any of the below actually ships. The order below is a dependency chain, not just a priority list — each item needs the one(s) before it.

1. ~~Backend + sync foundation.~~ **Done** — see "Sync backend (Supabase)" above. Chose Supabase over Cloudflare D1 + Durable Objects. Project, schema, and RLS exist; no client code uses it yet (that's items 2 and 3 below). Worth having done even before sharing exists: iOS Safari can evict all cached PWA data after 7 days of inactivity, so this also fixes a real data-loss risk for every current solo user, once an actual sync path is wired up on top.
2. ~~**Account-less identity layer.**~~ **Done** — see "Account-less identity layer" above. No login wall — a random `userId` (the row key, not secret, minted by Postgres via `gen_random_uuid()`) plus a separate per-device `deviceSecret` (the actual bearer credential, hashed server-side, never stored raw) generated the first time a user shares something or links a second device, not on every install. Linking a second device to existing data uses a short-lived (~10 min), single-use, server-minted pairing code exchanged for a fresh `deviceSecret` under the same `userId` — never reuse one device's secret on another, so a lost/stolen device is revocable without touching the rest. **Still missing**: any UI to actually trigger registration/pairing (deferred to item 3, since there's nothing to link/sync yet) — the manual JWT Signing Key setup is done and verified working. Add an *optional* recovery layer (magic link or Sign in with Apple/Google) on top of this later, offered as an upgrade, not a wall — it fixes the "lost every device, no pairing code" gap and puts a real ceiling on free-tier abuse (a bare UUID costs nothing to mint fresh via reinstall), at the cost of App Store guideline 4.8 (must also offer Sign in with Apple if any other social login is offered) and WebView OAuth restrictions if a Capacitor wrap ever happens.
3. ~~**Sharing feature: recipe → grocery list → meal plan cascade.**~~ **Done, and already revised twice** — see "Sharing feature: recipe → grocery list → meal plan cascade" above. Manual two-device testing against the real dev Supabase project surfaced three real bugs in the first pass (asymmetric bulk-share on pairing, push-before-pull data clobbering, and no debouncing) — all three fixed. A later bug report ("delete on one device never actually removed it") led to a second revision: account pairing is now understood as *the same person's* own devices (phone + tablet), fully symmetric including delete, not a stand-in for sharing with another person — see item 4 below for that. Current shape: no-per-item-opt-in sync-everything, pull-before-push, a 5s debounce on content-mutation syncs, symmetric delete with a durable pending-tombstone retry. Re-verify end-to-end with two real devices/browser profiles after any further sync-engine change, given how much this area has already moved.
4. ~~**Per-resource sharing: share one item with someone else's account.**~~ **Done** — see "Per-resource sharing (recipe → grocery-list → meal-plan, one item at a time)" above. A `resource_shares` grant table + RLS policies keyed on it, distinct from device pairing (item 3): a recipient can view and fully edit a shared item, but never re-share it, and their "delete" only ever revokes their own grant — the owner's delete still cascades to every recipient for free via the existing tombstone mechanism. Not yet manually re-verified end-to-end with two real separate accounts (only unit/component/integration-tested) — do that before relying on it in production, the same way item 3's real bugs were only found by actual two-device testing.
5. **Live push while both apps are open (optional enhancement).** A WebSocket/SSE connection, live only while both apps happen to be foregrounded at once — never load-bearing, silently falls back to item 3's sync-on-open otherwise. Don't build this in the same pass as item 3; ship sync-on-open first and see if the "both people standing in the store" case comes up enough to justify it. iOS kills background service workers/WebSockets within seconds of backgrounding and has no Background Sync API at all, so this can never be the backbone regardless.
6. **Monetization — two pieces on different timelines.** A **grocery-affiliate "order this list" button** (Instacart Developer Platform) doesn't need any of the above — it hangs off the grocery list that already exists today, solo device and all, so it's the one item on this list worth doing out of dependency order if an early revenue signal matters. A **freemium subscription** (free tier capped at N generations/month via the rate-limit item above, paid tier unlimited + more shared-kitchen seats) needs item 2's identity to exist and should wait until there's real usage to gate — no point building Stripe billing for zero users. Billing runs through Stripe on the web either way, not store IAP — Cookerist has no native app, so no App Store/Play Store commission (15–30%) applies at all.
7. **Native app / Capacitor wrap — deferred, not scoped.** Don't rewrite anything native. The one PWA weakness that matters (the iOS 7-day eviction risk) is already fixed by item 1 regardless of sharing. Revisit a Capacitor wrap of the same web codebase only if App Store/Play Store search-and-ratings discovery becomes an actual growth bottleneck once there are real users — a distribution decision to make later, not an engineering one now.
